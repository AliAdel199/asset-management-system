# تصميم قاعدة البيانات التحليلي

هذه الوثيقة تصف تصميم قاعدة البيانات المقترح على مستوى تحليلي تفصيلي. لا تمثل Prisma Schema، ولا تحتوي على كود، ولا تنشئ قاعدة بيانات فعلية.

## مبادئ التصميم

1. اعتماد سجل رئيسي للموجودات في جدول `assets`.
2. حفظ الحركة التاريخية في جداول مستقلة بدل الاعتماد على الحالة الحالية فقط.
3. منع الحذف النهائي للموجودات، واستخدام الشطب كعملية رسمية.
4. فصل البيانات العامة للموجود عن البيانات الخاصة بالتصنيف.
5. ربط الصيانة والمواد المصروفة والمرفقات بالموجود أو العملية ذات العلاقة.
6. تسجيل العمليات المؤثرة في جدول تدقيق مستقل.
7. دعم الصلاحيات حسب الهيكل الإداري متعدد المستويات.
8. ترك استيراد Excel كمرحلة لاحقة بعد تحليل الملفات.

## الجداول الأساسية

### organization_units

يمثل المؤسسة الرئيسية والجهات التابعة.

الحقول المقترحة:

| الحقل | الوصف | ملاحظات |
|---|---|---|
| id | معرف الجهة | مفتاح أساسي |
| parent_id | الجهة الأعلى | فارغ للمؤسسة الرئيسية |
| name | اسم الجهة | إلزامي |
| code | رمز الجهة | يستخدم في رقم الموجود |
| unit_type | نوع الجهة | مؤسسة، دائرة، قسم، شعبة، أو غير ذلك حسب الاعتماد |
| is_active | حالة الجهة | فعالة أو موقوفة |
| created_at | تاريخ الإنشاء | للتدقيق |
| updated_at | تاريخ آخر تعديل | للتدقيق |

العلاقات:

1. الجهة قد تتبع جهة أعلى من نفس الجدول.
2. الجهة ترتبط بالمستخدمين.
3. الجهة ترتبط بالموجودات كجهة مالكة أو مستلمة.

قيود مقترحة:

1. رمز الجهة يجب أن يكون فريدًا.
2. لا يجوز حذف جهة لها موجودات أو مستخدمون، ويمكن إيقافها بدل حذفها.

### users

الحقول المقترحة:

| الحقل | الوصف | ملاحظات |
|---|---|---|
| id | معرف المستخدم | مفتاح أساسي |
| organization_unit_id | الجهة المرتبط بها | إلزامي |
| full_name | الاسم الكامل | إلزامي |
| username | اسم الدخول | فريد |
| password_hash | كلمة المرور المشفرة | لا تخزن كلمة المرور نصًا |
| is_active | حالة المستخدم | فعال أو موقوف |
| last_login_at | آخر دخول | اختياري |
| created_at | تاريخ الإنشاء | للتدقيق |
| updated_at | تاريخ آخر تعديل | للتدقيق |

العلاقات:

1. المستخدم ينتمي إلى جهة واحدة.
2. المستخدم قد يمتلك دورًا أو أكثر من خلال `user_roles`.
3. المستخدم يظهر في `audit_logs` كمستخدم منفذ.

الحقول المقترحة:

| الحقل | الوصف | ملاحظات |
|---|---|---|
| id | معرف الدور | مفتاح أساسي |
| name | اسم الدور | فريد |
| description | وصف الدور | اختياري |
| scope_level | نطاق الدور | مركزي أو جهة أو قراءة فقط |
| is_active | حالة الدور | فعال أو موقوف |

الحقول المقترحة:

| الحقل | الوصف | ملاحظات |

قيود مقترحة:

1. منع تكرار نفس الدور لنفس المستخدم ضمن نفس النطاق.

| supplier_id | الجهة المجهزة | اختياري |
| book_value | القيمة الدفترية | قيمة ثابتة في النسخة الأولى |
| model | الموديل | اختياري |
| origin | المنشأ | اختياري |
| manufacture_year | سنة الصنع | اختياري |

| service_entry_date | تاريخ دخول الخدمة | اختياري |
| issue_document_number | رقم مستند الصرف | اختياري |
| daily_sequence | تسلسل اليومية | اختياري |
| document_date | تاريخ المستند | اختياري |
| notes | ملاحظات | اختياري |

قيود مقترحة:

1. `internal_number` فريد وإلزامي.
2. لا يسمح بحذف السجل نهائيًا.
3. إذا كان `serial_number_missing` يساوي نعم، يسمح بترك `serial_number` فارغًا.
4. إذا كانت حالة الموجود مشطوب، تمنع عمليات التسليم والنقل والصيانة الجديدة.
5. لا يجوز وجود مستلم حالي دون سجل تسليم فعال في `asset_assignments`.

2. يجب ربط الجدولة إما بموجود محدد أو بتصنيف.

## جداول الشطب والمرفقات

### asset_write_offs

يمثل شطب الموجود.

الحقول المقترحة:

| الحقل | الوصف | ملاحظات |
|---|---|---|
| id | معرف الشطب | مفتاح أساسي |
| asset_id | الموجود | إلزامي وفريد |
| document_number | رقم مستند الشطب | إلزامي |
| document_date | تاريخ مستند الشطب | إلزامي |
| approved_by_organization_unit_id | الجهة المخولة | اختياري حتى اعتمادها نهائيًا |
| approved_by_user_id | المستخدم المعتمد | اختياري |
| write_off_reason | سبب الشطب | اختياري |
| notes | ملاحظات | اختياري |
| executed_at | تاريخ تنفيذ الشطب | إلزامي |
| created_at | تاريخ إنشاء السجل | للتدقيق |

قيود مقترحة:

1. لكل موجود سجل شطب واحد فقط.
2. بعد الشطب، تصبح حالة الموجود مشطوب.
3. لا يتم حذف الموجود من `assets`.

### attachments

يمثل المرفقات المرتبطة بالموجود أو العملية.

الحقول المقترحة:

| الحقل | الوصف | ملاحظات |
|---|---|---|
| id | معرف المرفق | مفتاح أساسي |
| related_entity_type | نوع السجل المرتبط | `Asset`, `MaintenanceRequest`, `AssetMovement`, `AssetWriteOff` |
| related_entity_id | معرف السجل المرتبط | إلزامي |
| file_name | اسم الملف | إلزامي |
| file_type | نوع الملف | صورة أو PDF |
| file_size | حجم الملف | لا يتجاوز 10MB مبدئيًا |
| storage_path | مسار التخزين | يحدد لاحقًا حسب بيئة التشغيل |
| uploaded_by_user_id | المستخدم الرافع | إلزامي |
| uploaded_at | تاريخ الرفع | إلزامي |
| is_active | حالة المرفق | فعال أو ملغى |

قيود مقترحة:

1. منع أنواع الملفات غير المعتمدة.
2. منع تجاوز حجم الملف المعتمد.
3. لا يحذف المرفق فعليًا إذا كان مرتبطًا بعملية رسمية إلا وفق سياسة تعتمد لاحقًا.

الحقول المقترحة:

قيود مقترحة:

3. يسجل كل إجراء مؤثر على الموجودات والحركة والصيانة والشطب.

## قيود قواعد العمل على مستوى البيانات

1. لا حذف نهائي من جدول `assets`.
2. لا يوجد أكثر من تسليم فعال واحد للموجود في `asset_assignments`.
3. لا يوجد أكثر من سجل شطب واحد للموجود في `asset_write_offs`.
4. لا تسليم ولا نقل ولا صيانة جديدة لموجود حالته مشطوب.
5. لا اعتماد نقل قبل وجود جهة منقولة منها وجهة منقولة إليها.
6. لا إكمال صيانة دون تاريخ إكمال ونتيجة صيانة.
7. لا مادة مصروفة دون كمية وسعر وحدة.
8. لا مرفق بحجم أكبر من الحد المعتمد.
9. لا مستخدم دون جهة تنظيمية.
10. لا رقم موجود مكرر.

## ملاحظات حول Excel

1. لا تعتمد قاعدة البيانات على افتراض أن كل صف في Excel يمثل موجودًا واحدًا.
2. قبل الاستيراد يجب إنشاء وثيقة تحليل لقوالب Excel.
3. الاستيراد يحتاج مرحلة تحقق ومراجعة قبل إدخال البيانات إلى الجداول الأساسية.
4. قد تتطلب بيانات Excel جداول وسيطة لاحقًا مثل `import_batches` و`import_rows`، لكنها ليست ضمن MVP التشغيلي الأول.

## أسئلة متبقية قبل التنفيذ الفعلي

1. ما رموز الجهات الرسمية المستخدمة في `organization_units.code`؟
2. ما رموز التصنيفات الرسمية المستخدمة في `asset_categories.code`؟
3. هل يعتمد النظام جدول صلاحيات تفصيلي `permissions` أم يكتفي بالأدوار في النسخة الأولى؟
4. هل يتم تسجيل تصدير التقارير في `audit_logs` دائمًا؟
5. ما السياسة النهائية لإلغاء المرفقات الخاطئة؟
6. هل ستكون الجهة المخولة بالشطب جهة واحدة أم تختلف حسب التصنيف أو القيمة؟
