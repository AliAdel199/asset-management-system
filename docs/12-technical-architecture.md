# المعمارية التقنية المقترحة

هذه الوثيقة تحدد الاختيار التقني المقترح للنظام قبل بدء التنفيذ البرمجي. لا تحتوي على كود، ولا تنشئ مشروعًا، ولا تثبت مكتبات.

## القرار التقني الموصى به

التوصية المعمارية للنسخة الأولى:

1. الواجهة الأمامية: `Next.js`.
2. الخادم الخلفي وواجهات API: `NestJS`.
3. قاعدة البيانات: `PostgreSQL`.
4. طبقة التعامل مع قاعدة البيانات لاحقًا: `Prisma`.
5. التخزين: تخزين ملفات المرفقات على سيرفر المؤسسة أو مسار تخزين داخلي مع حفظ بياناتها في قاعدة البيانات.

## سبب اختيار المعمارية

### Next.js

مناسب لبناء واجهة إدارية عربية RTL، ويخدم شاشات الموجودات والصيانة والتقارير والبحث والتصفية بكفاءة.

مناسب لـ:

1. صفحات النظام الإدارية.
2. الجداول والفلاتر.
3. تجربة مستخدم متجاوبة للحاسوب والتابلت.
4. فصل واضح بين واجهة المستخدم والمنطق الخلفي.

### NestJS

مناسب كنظام خلفي منظم لوحدات حكومية كثيرة ومتشابكة.

مناسب لـ:

1. تنظيم الوحدات مثل الموجودات، الصيانة، النقل، الشطب، الصلاحيات.
2. ضبط الصلاحيات والتحقق قبل تنفيذ العمليات.
3. توفير API واضح للواجهة.
4. فصل قواعد العمل عن واجهة المستخدم.
5. قابلية التوسع مستقبلًا.

### PostgreSQL

مناسب لطبيعة النظام التي تعتمد على العلاقات والسجلات التاريخية.

مناسب لـ:

1. العلاقات بين الموجودات والجهات والمستخدمين.
2. سجل الحركة والتسليم والاسترجاع.
3. الصيانة والمواد المصروفة.
4. التقارير والفهارس.
5. سجل التدقيق.

### Prisma

يمكن استخدامه لاحقًا بعد اعتماد تصميم قاعدة البيانات، لأنه يساعد على إدارة نماذج البيانات والتعامل معها بشكل منظم.

ملاحظة: لا يتم تصميم `Prisma Schema` إلا بعد اعتماد التصميم التقني وقاعدة البيانات.

## البدائل التي تمت دراستها

| البديل | الوصف | سبب عدم ترجيحه |
|---|---|---|
| Next.js فقط | واجهة وAPI داخل نفس المشروع | مناسب للأنظمة الأصغر، لكنه أقل فصلًا لنظام حكومي متعدد الوحدات |
| NestJS فقط | API فقط دون واجهة مدمجة | يحتاج واجهة منفصلة على أي حال |
| Laravel | إطار متكامل وقوي | جيد، لكن اختيار JavaScript/TypeScript موحد بين الواجهة والخلفية أسهل للفريق إذا اعتمد هذا المسار |
| .NET | قوي للأنظمة الحكومية | خيار جيد إذا كانت المؤسسة تعتمد Microsoft بشكل كامل، لكنه يحتاج قرارًا مؤسسيًا |
| MySQL | قاعدة بيانات علائقية | جيد، لكن PostgreSQL أقوى في الفهارس والعلاقات والتقارير المعقدة |

## هيكل النظام المقترح

النظام يقسم إلى ثلاث طبقات رئيسية:

1. طبقة الواجهة الأمامية.
2. طبقة API والخدمات.
3. طبقة قاعدة البيانات والتخزين.

## طبقة الواجهة الأمامية

المسؤوليات:

1. تسجيل الدخول.
2. عرض لوحة التحكم.
3. عرض وإدارة الموجودات.
4. عرض تفاصيل الموجود.
5. تنفيذ إجراءات التسليم والاسترجاع والنقل والصيانة والشطب.
6. رفع المرفقات.
7. عرض التقارير وتصديرها.
8. عرض الرسائل والتنبيهات بالعربية.

لا تحتوي الواجهة على قواعد العمل الحساسة وحدها، بل تعتمد على API للتحقق النهائي.

## طبقة API والخدمات

المسؤوليات:

1. التحقق من هوية المستخدم.
2. تطبيق الصلاحيات.
3. تنفيذ قواعد العمل.
4. إدارة الموجودات.
5. إدارة الحركة والعهدة.
6. إدارة الصيانة والمواد المصروفة.
7. إدارة الشطب.
8. إدارة المرفقات.
9. توليد التقارير.
10. تسجيل العمليات في `audit_logs`.

## طبقة قاعدة البيانات

المسؤوليات:

1. حفظ بيانات الجهات والمستخدمين والصلاحيات.
2. حفظ بيانات الموجودات.
3. حفظ سجلات الحركة والتسليم والاسترجاع.
4. حفظ الصيانة والمواد المصروفة.
5. حفظ الشطب والمرفقات.
6. حفظ سجل التدقيق.
7. دعم البحث والتقارير عبر الفهارس المناسبة.

## المصادقة والصلاحيات

المقترح:

1. تسجيل دخول باسم مستخدم وكلمة مرور.
2. تخزين كلمة المرور بشكل مشفر.
3. ربط كل مستخدم بجهة.
4. ربط كل مستخدم بدور أو أكثر.
5. تطبيق الصلاحيات في API قبل تنفيذ أي عملية.
6. فلترة البيانات حسب جهة المستخدم وصلاحياته.

قواعد مهمة:

1. الواجهة تخفي الأزرار غير المسموحة، لكن API هو مصدر الحماية النهائي.
2. لا يسمح بالحذف النهائي للموجودات مهما كان الدور.
3. عمليات النقل والشطب تحتاج صلاحيات خاصة.

## إدارة المرفقات

المقترح للنسخة الأولى:

1. حفظ الملفات على سيرفر المؤسسة أو مساحة تخزين داخلية.
2. حفظ بيانات المرفق في جدول `attachments`.
3. دعم الصور وPDF.
4. حد مبدئي 10MB لكل مرفق.
5. ربط المرفق بالموجود أو الصيانة أو النقل أو الشطب.

ملاحظات:

1. مسار التخزين النهائي يعتمد على بيئة المؤسسة.
2. سياسة إلغاء المرفقات الخاطئة تحتاج اعتمادًا نهائيًا.

## التقارير والتصدير

المقترح:

1. توليد التقارير من API.
2. عرض النتائج في الواجهة.
3. دعم التصدير إلى PDF وExcel.
4. تقييد التقارير حسب صلاحيات المستخدم.
5. تسجيل عملية التصدير في `audit_logs` إذا اعتمدت المؤسسة ذلك.

التقارير الأساسية:

1. الموجودات حسب الجهة.
2. الموجودات حسب التصنيف.
3. الموجودات حسب الحالة.
4. حركة الموجود.
5. الصيانة.
6. المواد المصروفة.
7. الشطب.
8. المرفقات.

## النشر والتشغيل

المقترح:

1. نشر النظام على سيرفر المؤسسة.
2. تشغيل الواجهة والخادم الخلفي كخدمات مستقلة.
3. تشغيل قاعدة البيانات على سيرفر داخلي أو خادم قاعدة بيانات معتمد.
4. تفعيل HTTPS.
5. تفعيل النسخ الاحتياطي.
6. مراقبة الأخطاء والسجلات.

## النسخ الاحتياطي

المطلوب:

1. نسخ احتياطي دوري لقاعدة البيانات.
2. نسخ احتياطي لمجلد المرفقات.
3. اختبار استرجاع النسخة الاحتياطية بشكل دوري.
4. توثيق مسؤولية النسخ الاحتياطي ضمن تشغيل المؤسسة.

## الأمن

متطلبات أساسية:

1. HTTPS.
2. كلمات مرور مشفرة.
3. صلاحيات حسب الدور والجهة.
4. منع الوصول المباشر للملفات دون تحقق.
5. سجل تدقيق للعمليات المؤثرة.
6. رسائل خطأ لا تكشف تفاصيل تقنية حساسة.

## الأداء

اعتبارات الأداء:

1. فهارس على الرقم الداخلي والتصنيف والحالة والجهة.
2. صفحات نتائج للجداول الكبيرة.
3. فلاتر بحث واضحة.
4. عدم تحميل المرفقات الثقيلة ضمن قوائم النتائج.
5. تحسين تقارير الموجودات والحركة والصيانة.

## خطة الانتقال إلى التنفيذ

الترتيب المقترح:

1. اعتماد هذه الوثيقة.
2. تثبيت اختيار قاعدة البيانات.
3. إنشاء هيكل المشروع.
4. تصميم `Prisma Schema` بناءً على `10-database-design.md`.
5. تنفيذ المصادقة والصلاحيات.
6. تنفيذ الهيكل الإداري والبيانات المرجعية.
7. تنفيذ الموجودات.
8. تنفيذ الحركة والصيانة والشطب.
9. تنفيذ المرفقات والتقارير.
10. الاختبار والتشغيل التجريبي.

## قرارات تقنية تحتاج اعتمادًا قبل البرمجة

1. هل تعتمد المؤسسة `PostgreSQL` رسميًا؟
2. هل يكون التخزين داخل سيرفر التطبيق أم على مسار ملفات مركزي؟
3. هل يتم نشر الواجهة والخادم الخلفي على نفس السيرفر أم سيرفرين؟
4. هل المصادقة محلية فقط أم يوجد تكامل مستقبلي مع دليل مستخدمين داخلي؟
5. هل تسجل عمليات تصدير التقارير في `audit_logs`؟
6. ما سياسة النسخ الاحتياطي المعتمدة؟
7. ما بيئة التشغيل المتاحة على سيرفر المؤسسة؟

## حدود هذه الوثيقة

1. لا تنشئ مشروع `Next.js`.
2. لا تنشئ مشروع `NestJS`.
3. لا تثبت أي مكتبات.
4. لا تنشئ قاعدة بيانات.
5. لا تصمم `Prisma Schema`.
6. تمثل قرارًا معماريًا وتحضيريًا قبل التنفيذ.
